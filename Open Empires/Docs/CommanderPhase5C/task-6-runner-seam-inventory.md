## Native outcomes and bounded capture

- `Assets/Scripts/Commands/CommandBuffer.cs:CommandEnqueued` distinguishes Human/Commander enqueue origins; `FlushCommands()` is the normal buffer seam. It exposes raw command objects (unit IDs, target coordinates, etc.), so an external record must project safe type/count/origin fields, not serialize commands.
- `Assets/Scripts/Core/GameSimulation.MovementObservation.cs`: `NativeMoveProcessed` carries a local receipt with runtime/original-command identity, unit, tick, endpoint, and path result; `NativeUnitCommandProcessed` observes processed unit orders. The ordinary processing path publishes from `GameSimulation.ProcessCommand` / `ProcessMoveCommand`. Runtime receipt objects are internal and contain IDs/coordinates: retain only permitted completion/result facts in the durable corpus.
- `Assets/Scripts/AI/Commander/Phase5A/CommanderGoalManager.Production.cs`: `HandleTrainingAccepted` / `HandleTrackedUnitProduced` use native `TrainingOrderReceipt` attribution and exact result IDs. `CommanderGoalManager.GoalEventPublished` / `GoalStatusChanged`, plus `Phase5B/CommanderTaskBoardProjection.Capture(...)`, provide status/progress snapshots. Task-board snapshots are detached, but include IDs, player/runtime tokens and text; project an allow-list and omit identifying fields before persistence.
- Safe draft inspection exists in `CommanderPendingClarification.Serialize()` and `CommanderRequestGraphDraft` projections; action-plan preview is `CommanderActionPlanCandidate.Preview`. These are observation sources, not a versioned scenario/result recorder.
