### Important (should fix before freeze)

1. **Repeated anchored construction is advertised in a non-admittable Request shape.** `Assets/Scripts/AI/Commander/Phase5C/CommanderSemanticRequestPack.cs:92-99,215` advertises `BuildStructure` count `1..20` with optional anchored placement, but only includes the working DynamicPlan vocabulary for narrow `build|construct|make` + immediate number forms. `Assets/Scripts/AI/Commander/CommanderIntentValidator.cs:171` rejects every anchored static `BuildStructure` with count other than one. A legitimate request such as “Place two Houses near my Town Center” triggers the construction contract but not the dynamic contract; a schema-valid two-House placed Request is then rejected, not executed. Even “Build two Houses” has two conflicting advertised representations. Align the compact contract with admission: advertise anchored static count one only, retrieve the repeated-build dynamic route for explicit N-plus-anchor forms beyond that regex, and add a production-pack/admission regression for such wording. Do not weaken the whole-plan site preflight or execute a prefix.

2. **Partial garrison is marked as a completed player objective.** `Assets/Scripts/AI/Commander/CommanderPlanner.Garrison.cs:148-151` returns `CommanderGoalStatus.Completed` once all *issued* entrants are housed, regardless of `requested`/unaccommodated/protected count. The focused partial-capacity test explicitly asserts `1/3` housed **and** `Completed` (`Assets/Tests/EditMode/CommanderPhase5ADynamicRuntimeTests.cs:668-692`). `CommanderTaskBoardProjection.cs:171,184` maps that to a Completed card for “garrison all villagers,” moving it into completed history despite two still exposed. The detail text reports `1/3`, but the headline status is false. Keep the exact native order and numerical remainder, but terminate an unmet all/count objective as a truthful partial/blocked status (or an explicit partial terminal state) and assert the task card does not say Completed for `1/3`. Do not issue recovery or substitute actors.

3. **Real-route per-objective metrics are not durably correlated or exportable.** `Assets/Scripts/AI/Commander/Phase4A/OpenRouterCommanderProvider.cs:92-103,125-140` keeps initial/repair estimates, actual nullable usage, cost and stages only as `Last*`/bounded 32-attempt in-memory properties; `CommanderChatUI.cs:483` mints a request ID but does not join those attempts to its admitted objective or persist them. The Phase 5C recorder is test-only (`Assets/Tests/Shared/ScenarioEvidenceRecorder.cs:72-92`), while offline corpus rows intentionally leave actual usage/cost and transport timing null (`CommanderEconomyClarificationTests.Phase5CCorpus.cs:1105-1116`). A standalone Windows or served-Web request followed by refresh/exit can therefore lose the actual usage/attempt record needed for the brief's per-request input/cost/latency and cost-per-fulfilled-objective report; a screenshot cannot recover it. Add a bounded, privacy-safe production observation/export seam keyed by the game-owned request ID and initial/repair attempt, joining admission/task outcome and separately timed stages where available, with a Web-accessible export path. Missing provider usage stays unknown. A separately maintained operator ledger can enforce the ten-call *test allowance* without changing gameplay source, but it cannot substitute for actual usage/cost or causal per-objective evidence.
