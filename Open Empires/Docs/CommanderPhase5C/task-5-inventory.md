## Current runtime surface and seams

- `Assets/Scripts/AI/Commander/Phase4A/CommanderChatUI.cs`: `CreateLocalWindow()` creates the local-only UI after scene load. `Awake()` calls `EnsureLocalSurface()` then hides `canvasRoot`; `Initialize()` resets runtime-affine state, increments `runtimeGeneration`, initializes presentation, and also hides/minimizes via `InitializePresentation()`. `SubmitMessageAsync()` is the real submission path. Existing request/lifetime cancellation, generation checks, `submitting` guard, pending plan preview and strategy approval bridge are central lifecycle seams; preserve them rather than building a parallel controller.
- `CommanderChatUI.BuildUI()` (same file, around line 992) constructs Canvas/CanvasScaler, panel, transcript scroll, input field, buttons and legacy status/approval rows. It calls `BuildPresentationUI()`. This is the main structural refactor seam; Canvas scaler is `ScaleWithScreenSize`.
- `Phase4A/CommanderChatUI.Presentation.cs`: `BuildPresentationUI`, `UpdatePresentation`, `ReviewCard`, `CompactButton`, `OpenCommander`, `MinimizeCommander`, `ContainsScreenPoint`, `ClaimPresentationAction`, `OnDraftChanged`. Current launcher is a 310px panel at the lower-right offset; its compact stack includes voice and Text AI settings, status, task board, transcript review and approval. Expanded layout has a compact approval/review card and minimize control but no Chat/Tasks tab architecture. `ClaimPresentationAction()` prevents two physical UI actions in one frame; `UpdatePresentation()` shows approval/review and currently uses the shared status projection. Voice cancel visibility is tied to recording/transcription, not semantic request cancellation.
- `Phase5B/CommanderChatUI.TaskBoard.cs`: `BuildTaskBoardUI()` and refresh/projection bind the task board. It consumes `CommanderTaskBoardProjection.Capture(...)`; active cards are ordered separately from history and `TryCancel(...)` validates runtime token and task identity before cancel. Keep this typed projection/control path; avoid deriving task truth from transcript text.
- `Phase5B/CommanderTaskBoardProjection.cs`: `CommanderTaskBoardSnapshot`, `CommanderTaskCardSnapshot`, `CommanderTaskBoardProjection.Capture` and `TryCancel`. Snapshot has objective/progress/current step/blocker/status/can-cancel/steps. This is reusable for readable cards and explicit Cancel.
- Approval projections are split across `CommanderChatUI.ActionPlans.cs` and `CommanderChatUI.StrategicControls.cs`; presentation currently uses `pendingActionPlan?.Preview`, otherwise generic strategy text. Existing buttons and admission/confirmation methods are authority-bearing seams: display details must not be made approval actions, and labels must not replace structural approval checks.
- Settings surfaces already exist in separate partials: `CommanderChatUI.VoiceSetup.cs`, `CommanderChatUI.ProviderSetup.cs`, `CommanderChatUI.LocalModels.cs`. They are constructed by presentation but hidden as separate cards; preserve voice/audio-consent vs reviewed transcript submission vs semantic provider setup distinctions.
- Voice review is represented by `compactReview` (`Review transcript — not submitted`) and its Send/Edit/Discard callbacks. `voiceOwnedDraft`, `inputRevision`, `voiceDraftRevision`, `ReleaseVoiceDraft()` protect reviewed text from clobbering user edits. Keep this review route and avoid auto-submitting a transcript.

## Input ownership and request recovery

- `CommanderUIInputGuard.IsPointerOverCommander` routes live mouse/virtual-cursor position through `CommanderChatUI.ContainsScreenPoint()`. `IsEditingText` checks the selected active TMP/legacy input field. `UnitSelectionManager` and gameplay input dispatch use these ownership checks; expanded dock geometry must stay truthful and minimized UI must not claim the screen.
- `TryHandleEscapeInput()` synchronously intercepts Escape for voice operations, setup surfaces, or expanded UI. `ClaimPresentationAction()` is same-frame single-fire for physical clicks/Enter. Keep click/Enter approval and submission mutually exclusive and verify gameplay input doesn't receive text/keys.
- Runtime replacement/reset increments `runtimeGeneration`, cancels/disposes `lifetime`, clears pending clarification/action plan and transcript; async callbacks already check generation/lifetime. `CommanderAIIntentAdapter.DefaultProviderTimeout` is 15 seconds and `OpenRouterCommanderProvider` also defaults to 15 seconds. UI `SubmitMessageAsync` uses per-request cancellation and `submitting`, but inventory did not find a dedicated user-facing semantic Retry/Edit/Cancel lifecycle. Add controls at the UI boundary that retain the draft and are single-use; do not add automatic retry or fallback. Cancellation should invalidate late results through existing request/runtime identity.
- Status risk: task-board status belongs to a selected/older card while `commanderStatusText`/`LatestSubmission` represent latest interaction. The presentation compact status prioritizes `submitting`, approval, transcript review, then `commanderStatusText`, while task cards are separately projected. A new request needs an explicit latest-request status projection that cannot be overwritten by a selected historical task.

## Minimal refactor recommendation

1. Keep `CommanderChatUI` as the single runtime owner and add a focused Phase5C presentation partial (or refactor `Presentation.cs`) for dock geometry and Chat/Tasks/settings navigation; preserve existing `BuildUI`, voice review, task projection, authority callbacks, and input-ownership methods.
2. Build an opaque graphite dock clamped to safe area at 380–460px desktop width, with a minimized launcher/badges that remains minimized at match start. Expanded Chat view uses one transcript scroll region and bottom-fixed multiline composer; Tasks view uses active cards then collapsed history. Settings stays separate. Dock geometry should be tested at 1280×720, 1920×1080 and the reported scaled Editor viewport, away from HUD/minimap.
3. Add an immutable/latest request presentation state independent from selected task card; map actual submission/admission/task facts to the named statuses in the brief. Put visible Cancel and Retry/Edit on pending/timeout request state and always-visible task Cancel on active task cards. Keep approval cards/buttons visible with bounded effect/source/count/order/binding details sourced from validated plan data.
4. Do not create a new authority path: route approval/cancel through current plan/task controls and retain frame-level action claim + request/runtime generation guards. Do not let panel minimize disable controllers or tasks, and do not auto-open on replies.
