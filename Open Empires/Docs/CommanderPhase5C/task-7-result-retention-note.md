This is not a retained per-leaf pass record: the empty failure list is only progress evidence, not proof that all four passed.

The `includeDetails` flag on `run_tests` is not retained by the MCP job. `Editor/Tools/RunTests.cs:43-58` reads and echoes it, then starts the job without that flag. `Editor/Tools/GetTestJob.cs:22-32` reads it on each poll. With a result present, `TestRunnerService.cs:609-636` returns a summary regardless of `includeDetails`; the flag only controls the leaf `results` array. Thus, omitting details on the start call alone cannot explain `result:null`.

There is a concrete result-loss mechanism: `TestJobManager.TryRestoreFromSessionState` reconstructs persisted jobs with `Result = null` (`Editor/Services/TestJobManager.cs:163-210`, comment at 208). A domain reload before polling can therefore preserve terminal status/progress but lose leaves. The recovered JSON does not establish that this particular job reloaded. Another source-supported possibility is the task-continuation fallback: `FinalizeFromTask` marks a completed task with null `task.Result` as succeeded and stores null (`TestJobManager.cs:637-677`). Normally the `TestRunnerService.RunFinished` path builds a `TestRunResult` from the run result and leaf adaptors, then hands it to the job manager (`TestRunnerService.cs:321-333`, `369-405`). Consequently, the exact cause for this job remains unconfirmed without evidence of its callback/reload timeline.

## Available retention seams

- **Existing run, if Test Runner still holds it:** Unity Test Runner's “Export Results” control is enabled when `m_LatestTestResults` is non-null and calls `TestRunnerApi.SaveResultToFile` (`UnityEditor.TestRunner/GUI/Views/TestListGUIBase.cs:40, 110, 187-195`); its `RunFinished` stores that result at line 515. This can export without a rerun, but only while that editor window/session still retains the result. No XML named for job `5c68450293874847985f9e0d982ec7b5` was found in the Phase 5C evidence file inventory; absence there does not prove no XML exists elsewhere.
- **Callback at the actual final run:** the installed Test Framework exposes `ICallbacks.RunFinished(ITestResultAdaptor)` and per-node `TestFinished` (`UnityEditor.TestRunner/Api/ICallbacks.cs:8-29`). Register with `TestRunnerApi.RegisterCallbacks<T>` (`Api/TestRunnerApi.cs:100-130`); at `RunFinished`, `TestRunnerApi.SaveResultToFile(result, uniqueXmlPath)` writes NUnit XML (API lines 191-198). The adaptor exposes `FullName`, `ResultState`/`TestStatus`, `Duration`, `Message`, `StackTrace`, `Output`, and `Children` (`Api/ITestResultAdaptor.cs:20-112`); the callback can therefore preserve exact leaf identity, pass/fail/skip, timing, and diagnostics. The built-in XML writer writes the complete result tree via `result.ToXml()` (`Api/ResultsWriter.cs:64-99`). Register before the final job; write to a unique per-job path because the API overwrites a matching path. An editor-only callback is a possible gate instrument, not yet implemented or verified for registration survival across domain reload/PlayMode transitions.
- **MCP polling while memory is intact:** poll `get_test_job` with `includeDetails:true` (and optionally `includeFailedTests:true`). The MCP runner collects leaf adaptors and normally materializes a `TestRunResult` in `RunFinished` (`TestRunnerService.cs:321-333, 369-405`). If the job has already been restored with null `Result`, the current MCP cache has no leaf payload to recover; the persisted `SessionState` intentionally omits it (`TestJobManager.cs:208-210`).
- **CLI route only when selected before starting that run:** the installed command-line result callback saves XML on `RunFinished` (`CommandLineTest/ResultsSavingCallbacks.cs:24-37`); `-testResults`/`-editorTestsResultFile` supplies an explicit path (`CommandLineTest/SettingsBuilder.cs:98-110`). The package default is a timestamped project-root `TestResults-*.xml`, but the repository's historical evidence includes a shared `TestResults.xml` path, so use a unique explicit path for any future CLI run. This is not a way to attach retention retroactively to the already-finished MCP job.

## Conclusion / gate implication

If it cannot, the four leaf outcomes for this job are not reconstructable from its recovered MCP record. For the next single final gate, ensure a callback registered before the existing planned run writes native NUnit XML (or equivalent per-leaf JSON) from `RunFinished` to a unique durable artifact, then hash and retain it alongside the MCP job record. Validate callback lifecycle before relying on it; do not launch a parallel runner or infer leaves from progress counters.
