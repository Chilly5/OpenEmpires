This is a verdict on the frozen first CORE checkpoint, **not** whole Task 1, Phase 5C, a current-source identity, or native/runtime acceptance. ## Independent verdicts

- **Spec compliance: PARTIAL, with CORE contract blockers.** The package installs an estimated initial-request preflight and a separate repair preflight, retains the full supplied utterance/memory/pending/facts strings rather than truncating them in the packer, and keeps provider data outside execution authority. It does **not** yet meet §3's supported-family retrieval and no-fidelity-loss contract. Strictly `<4,000` *actual* input tokens on Windows and Web remains unproven and is correctly not claimed by the checkpoint.
- **Code quality: needs correction before CORE sign-off.** The packer is small, bounded, and fail-closed when its estimate exceeds the threshold; the columnar knowledge projection preserves each retained row's values and null positions. But keyword-gated schema selection, incomplete schema generation, and final-attempt-only metrics make the implementation brittle. Green packing tests establish payload size for their fixtures, not correct interpretation of a supported order.

## Findings (ordered by effect)

1. **P1 — Supported typed family silently disappears from the compact contract.** The frozen packer's selection set is populated only from hand-listed families and action-enum names (`evidence/task-1-core-review-package.md:207-228`); `Vocabulary` has no `SetResourceAllocation` case and silently falls through its `default` (`:267-301`). The existing strict parser and tactical admission do support that semantic node (`Assets/Scripts/AI/Commander/Phase4E/CommanderSemanticJson.cs:214-218`; `Assets/Scripts/AI/Commander/Phase4E/CommanderSemanticAdmission.cs:64-74`, consulted only for this named risk). A player request to set an allocation therefore lacks an advertised valid form even when the normal legacy contract had one. This violates the brief's requirement for one coherent contract derived from supported registrations; an omitted retrieval result must not be treated as lack of a mechanic. A coverage check must enumerate *all* admitted families, including the legacy one, and prove either a safe advertised form or a deliberately documented retirement—not just test a few utterances.

2. **P1 — Exact-word retrieval can suppress a needed capability family, and the fallback does not save mixed requests.** Family choice uses an exact-token `Has` list (`:202-216`), while the all-family fallback runs only if **no** category matched (`:215-216`). For example, “send spearmen to guard my Gold mine” matches production/allocation/construction via `spearmen`/`gold`/`mine`, but neither `send` nor `guard` is an action trigger (`:207-214`); `DefendArea` is consequently absent from `Action type` (`:225-228`, `:293-298`). This is a deterministic pack-selection defect, not evidence that the model will always misinterpret that sentence. It can make a valid compound intent unexpressible or encourage a narrower, wrong plan. The repeated-build/DynamicPlan gate has the same shape: “split all idle villagers between Food and Wood” matches allocation and `split`, but no construction, so the registered `partition-workers` path is omitted despite `DynamicVocabulary` containing it (`:207-235`, `:304-315`; registry is `Assets/Scripts/AI/Commander/Phase5A/CommanderDynamicPlan.cs:85-89`). Retrieve by supported capability/representation needs and test mixed-domain and synonym cases, including split without construction.

3. **P1 — The advertised action form cannot preserve the supplied ALL/current-assignment/composed-location case.** The compact contract lists action selectors only as `Military|Scout|Villagers|Spearman|Archer|Knight|DamagedMilitary`, `count1..50`, and a single location enum (`:293-300`). There is no action-side AllMatching snapshot, current-Wood-worker filter, or “visible Wood/Tree west of selected owned TC” composite; worker `AllMatching` and `currentResource` are advertised only for `AllocateWorkers`, whose destination is a resource/source (`:277-278`). Consequently the brief's `move all of Wood villagers to the woodline left of my Town Center` cannot be represented losslessly by these exposed forms. The common prose says to preserve quantities/restrictions (`:262-265`) but cannot make a missing typed field valid. Until a bounded adapter/form exists, the provider must be directed to Clarify/Unsupported rather than silently converting ALL to a count, dropping the Wood-worker criterion, or treating the woodline and TC side as separate targets. This is a contract limitation at this CORE checkpoint, not a claim that the later Task 2 action implementation is finished.

4. **P2 — Knowledge rows are lossless only *after* an upstream bounded retrieval, while capability identity is removed.** Within a retained nonempty row group, the `Columns`/positional-array conversion preserves field names, field values, cost component order, and explicit nulls (`:330-355`); this part is sound. But the projection drops top-level `canonicalUnitIds`, `canonicalBuildingIds`, and capability/selector lists and omits empty knowledge arrays (`:318-368`). The only `capabilitySupported` hint is attached to already-retrieved unit/building rows when it differs from availability/executability (`:325-344`). The existing knowledge retriever returns at most eight combined unit/building entries (`Assets/Scripts/AI/Commander/Phase5B/CommanderKnowledgeRetrieval.cs:13-14,49-53`), so the compact context cannot recover a referenced family/name that retrieval missed or distinguish a missing row from unsupported content. This is not an authority escalation—the fields remain detached hints and admission is game-side—but it does defeat the stronger “all requested relevant facts survive” claim until retrieval coverage is proved for compounds, pending drafts, and ambiguous names. Tests `:480-499` check size/dispatch, not which required facts survived.

5. **P2 — Usage observation is typed but not a per-attempt account, and a malformed object still says “reported.”** `PostAndExtractTextAsync` resets `LastUsage` before each HTTP attempt (`:113-120`) and then reads the response envelope (`:134-141`). A valid initial usage record is overwritten by `Unknown` and then repair usage when the eligible repair occurs (`:89-100`). `LastInputEstimate` and `LastInputSectionEstimates` refer only to the initial pack (`:75-81`); the repair estimate is checked but not retained as a separate attempt (`:92-99`). Thus the public observation cannot compute full attempt count/cost or account for a first paid call followed by repair, exactly as the checkpoint's open-gate list says. Additionally `HasReportedUsage` is `true` for any `usage` object, even `{}` or one with only invalid fields, while all metrics remain null (`:394-412`). Consumers must not interpret that flag as known prompt usage. Missing/invalid numeric values themselves correctly remain null, not zero (`:414-420`), and a malformed usage envelope does not poison a valid semantic reply in the supplied test (`:502-513`).

6. **P2 — The 8 focused tests are pack/transport tests, not fidelity or hard-cap proof.** The capture transport always returns a fixed `Answer` (`:548-561`). Tests assert calls, estimates, one untruncated utterance, and usage parsing (`:443-542`); they do not assert advertised family sets, all source constraints/columns, schema-valid but semantically wrong outputs, repaired-call metrics, or actual endpoint input tokens. The production-context tests instantiate `ContextBuilder`, which is useful, but only assert that the request was sent and estimated under 4,000 (`:480-499`). No Windows direct/Web gateway side-by-side section audit, gateway-added prompt measurement, endpoint/model tokenizer calibration, or actual usage certificate appears in this frozen CORE evidence. The report already labels those as open (`task-1-core-report.md:15-18`), so this is an evidence boundary, not a criticism of the stated partial claim.

## Confirmed strengths and boundaries

- Both initial and permitted repair bodies are estimated before dispatch, and over-limit repair is rejected without sending it (`evidence/task-1-core-review-package.md:55-105`); UTF-8 byte units plus 256 are explicitly described as an estimate, not actual model tokens (`:167-195`). This is a useful conservative local guard, but a fixed margin cannot certify an unverified rolling alias or gateway overhead.
- The packer keeps supplied text, semantic memory, question facts, and pending clarification in the user message instead of slicing them to fit (`:236-255`). Its positional knowledge tables do not themselves discard retained row values (`:345-353`). Upstream construction of those strings and upstream retrieval are separate fidelity gates.
- The provider still sends semantic JSON through the existing strict parser (`:83-105`); the packer itself does not choose runtime identities, coordinates, actors, approval, or commands (`:164-165`, `:262-265`). `capabilitySupported` is a detached observation (`:340-344`), not executable authority. This review found no CORE change that mints game authority from provider output. Schema-valid English accuracy remains unproven.
