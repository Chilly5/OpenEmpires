## A. Architecture changes

Phase 4D adds player-scoped strategic plan controls without moving execution authority out of the deterministic planner. Exact whole-form offline pause, resume, cancel, and status requests become typed `StrategicPlanControlRequest`s. The planner checks trusted owner, plan ID, creation tick, revision, lifecycle state, and current context. Pause freezes future plan milestones and plan-owned work while preserving already-dispatched atomic actions and completed world state; resume continues the same plan; cancel terminates future work and releases only the cancelled plan's reservations. Host callbacks also bind to their pipeline/runtime generation, so a numerically identical plan in a new runtime is not a valid stale target.

Plan health is a detached, bounded snapshot of owned approved state: status, typed wait/blocker, copied resource/population/production facts, and milestone/goal progress. It uses simulation ticks and real progress, not wall-clock guesswork or explanation text. A temporary resource or population prerequisite can recover inside the approved template without a second approval. A material objective, target, or budget change becomes a copied `StrategicAdaptationProposal` and remains inert until explicit player Confirm reuses the established approval → decision policy → planner route. An old plan remains active while a new recommendation is merely pending; replacement cancels old plan work and reservations through the existing lifecycle authority.

The offline `StrategicAdvisoryFeed` consumes only copied plan/health transitions, emits bounded fog-safe informational messages on meaningful changes, deduplicates per plan/version, and resets with the host. The host observes all owned active plans, including non-selected health-only changes. After reset/reinitialize, it silently seeds current owned plans so their first real subsequent transition is not lost or duplicated. Advisories never submit intent, approve, call a provider, or execute a command.

The final whole-source review found a constructor/host binding hole: a pipeline could be built with a simulation or goal manager different from its planner and bind callbacks before the mismatch was rejected. Behavioral REDs preceded exact constructor context validation and a host same-simulation guard. The guard preserves supported same-simulation planner replacement. A separate advisory reset RED/GREEN closed the first-transition edge. The final accepted full suites ran after these fixes.

## D. Safety boundaries

The LLM/provider can translate a player utterance into a bounded recommendation; it cannot call planner lifecycle APIs, approve an intent, create a goal, reserve resources, access hidden simulation state, or enqueue a `CommandBuffer` action. The local host routes exact lifecycle commands offline and takes trusted owner identity from its initialized simulation. Only explicit player approval/Confirm enters the existing policy and planner; a pending recommendation or advisory has no execution effect. Planner-owned IDs/revisions and host generation/context checks reject stale, foreign-owner, cross-match, and mismatched-context actions before mutation. The final constructor guard validates planner, simulation, and goal-manager identity before callback binding.

Health, proposal, and advisory values copy bounded owned/approved/known facts and do not retain live Unity, planner, goal-manager, simulation, or command objects. No enemy hidden-state diagnosis or new strategic objective was added. Pause/cancel/replacement preserve plan-scoped reservation accounting; the A–E PlayMode scenarios check no duplication, old-plan resurrection, cross-plan mutation, or terminal leak for the tested templates. The provider migration to OpenRouter Luna was a separate user-requested adjacent change; final static audit found no direct provider-to-planner/goal/command/simulation execution reference. Local `.env` exists but is ignored and untracked; its contents were not read. Multiplayer remains trusted-host/owner-scoped, not a networking redesign.

## G. Limitations and deferred work

- Phase 4D supports the existing RangedReinforcement and DefensiveTurtle strategic templates; new technology, siege, naval, autonomous objective switching, and Phase 4E features remain outside this phase. `NeedsPlayerDecision` advisory is deferred because no typed 4D.2 evidence category supports it; the system does not infer motive from a long wait.
- The Phase 4C opportunistic House wood cost is not a static strategic reservation; tested population recovery is deterministic but does not turn the reservation design into a general resource guarantee. The user's tactical “make 10 spearmen” playthrough reached a wood shortage and reported no eligible owned villager for the next Spearman. That tactical worker/reachability behavior has not been repaired or re-tested here, and Phase 4D readiness does **not** mean that request is robust.
- Under an arbitrary throwing external observer during replacement, old-plan cleanup completes and the exception propagates before the new plan is inserted; the player must retry. This is not a general all-or-nothing transaction. The reviewed residual does not grant provider/advisory authority or leak reservations, but a future broader observer-isolation design may improve UX. A minor active-adaptation explanation-dismissal test gap and unmeasured large-match health-presentation cost remain documented.
- Scenario F does not exercise a full Unity scene/bootstrap teardown. Multiplayer ownership tests protect the local trusted-host boundary; no networking redesign or broad network-runtime proof is claimed. Final Unity TestRunner/recovery scenes (three untracked scene/meta pairs) were observed, classified, excluded from implementation manifest, and retained without deletion. External Antigravity review is prepared but has not run; it may identify follow-up issues.
