## First failing layer and source trace

1. **Confirmed production defect, implicit restriction on resource placement.** The provider's BuildStructure contract exposes `MyTownCenter`, `MyBarracks`, and `WorkedResource`, but no visible, unworked resource anchor ([OpenRouterCommanderProvider.cs](../../Assets/Scripts/AI/Commander/Phase4A/OpenRouterCommanderProvider.cs), lines 26–33). The strict semantic parser likewise accepts only those placement anchors ([CommanderSemanticJson.cs](../../Assets/Scripts/AI/Commander/Phase4E/CommanderSemanticJson.cs), lines 127–174). The planner routes a `WorkedResource` anchor to `PlanWorkedResourceBuilding` ([CommanderPlanner.cs](../../Assets/Scripts/AI/Commander/CommanderPlanner.cs), lines 923–930). That path returns `Blocked` before builder selection when `TryResolveWorkedResource` fails (lines 975–1002); the resolver requires the resource node ID to be targeted by an owned villager and currently visible ([CommanderSemanticReferenceResolver.cs](../../Assets/Scripts/AI/Commander/Phase4E/CommanderSemanticReferenceResolver.cs), lines 75–96). This exactly matches the live blocker. “Near the woodline” did not authorize that extra requirement. The fix needs a game-owned visible-resource placement path or a truthful refusal/clarification if a requested location cannot be represented; simply selecting a worker cannot cure this anchor mismatch.
2. **Confirmed communication defect.** The accepted BuildStructure response generator unconditionally says “I will construct” before placement feasibility is known ([CommanderResponseGenerator.cs](../../Assets/Scripts/AI/Commander/CommanderResponseGenerator.cs), lines 10–34). The UI appends that admission response before the goal's later planner blocker ([CommanderChatUI.cs](../../Assets/Scripts/AI/Commander/Phase4A/CommanderChatUI.cs), lines 605–629). In the live match the top status remained “Understood. I will construct 1 lumber yard” while the task card was blocked and then failed. The task card did eventually contain the true blocker, but it took scrolling a short panel to see the `Current:` line and later the 1800-tick failure.
3. **Construction completion logic appears structurally correct but was not exercised to completion.** The planner's unplaced and semantic-placed branches require a completed building before marking `Completed` ([CommanderPlanner.cs](../../Assets/Scripts/AI/Commander/CommanderPlanner.cs), lines 315–425). The task projection's BuildStructure progress is completed buildings rather than assigned workers ([CommanderTaskBoardProjection.cs](../../Assets/Scripts/AI/Commander/Phase5B/CommanderTaskBoardProjection.cs), lines 135–167 and 224–225). This source inspection does not disprove the user-reported worker-assignment/task-reporting issue for a provider-produced compound plan; no such plan was run here.
4. **The House blocker is not a Commander defect.** The game had 0/10 population when the House order was processed. The planner reports no builder if it cannot select an owned living villager ([CommanderPlanner.cs](../../Assets/Scripts/AI/Commander/CommanderPlanner.cs), lines 937–942). The screenshot and card agree with that state.

The specific normalized provider node arrays, introduced `PreferredWorkers` or `ProtectedResource` constraints, approval tokens, and goal IDs were not exposed by this packaged UI. The inferred `WorkedResource` path is supported by the exact blocker string and control flow; it is not a claimed capture of Luna's JSON. No hidden-information access or unauthorized strategic goal was observed in the submitted requests.

## Usability observations and priorities

- **P0, confirmed production defect:** a common, reasonable “near woodline” order admits a goal but fails because construction uses a `WorkedResource` anchor the player did not request. The explicit one-idle-villager variant fails in the same first layer. Add bounded visible resource anchoring with deterministic, visible, reachable placement and worker selection; preserve genuine explicit worker and protected-resource constraints. Verify no work requirement is silently introduced.
- **P1, confirmed communication defect:** immediate “I will construct” reads as action underway while the goal can already be blocked on an unavailable anchor. Make interpreted, awaiting approval, accepted, working, blocked, and completed states distinguishable. Put the actionable blocker in the first visible task-card line and update the chat/status promptly when the task blocks or fails. The tiny task viewport required scrolling to read the reason.
- **P1, unverified:** a compound request may show a worker-assignment step complete before its requested building is complete. The current BuildStructure goal and card code appear to use completed-building counts, so reproduce the reported compound wording and inspect the whole request card before changing completion logic.
- **P2, unverified:** omitted builder count may affect Mill or default construction differently from the lumber-yard pair. The two observed lumber orders failed at anchor resolution before builder selection, so they do not establish a worker-default defect. Test the mandatory Mill pair in a legitimate state with visible, unworked berries and again with worked berries.

As a player, I had to scroll the task card to understand why a confidently acknowledged order produced no building. Rephrasing with “one idle villager” did not help in this state. The visible game gave no indication that a woodline had to be worked first. The later House blocker was understandable once combat had visibly removed the villagers. No approval preview occurred in these three single-node submissions, so approval discoverability remains unverified.
