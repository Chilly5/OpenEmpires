# OpenEmpires Commander Phase 4E — design

Status: user-approved architectural direction on 2026-09-26, including the explicit footprint-gap placement correction. This design implements the user's full Phase 4E objective (`Docs/CommanderPhase4E/phase4e-specification.md`), not a reduced natural-language demo. Source baseline: `Docs/CommanderPhase4E/phase4e-source-baseline.json`; live-source inventory: `Docs/CommanderPhase4E/phase4e0-architecture-investigation.md`.

## Intent and non-negotiable boundary

A normal player types supported outcomes in ordinary language and sees them converge in an easily playable Windows x64 build. The model describes semantic intent only. Trusted game code validates it, resolves owned/known references, derives legal prerequisites, arbitrates workers/resources/strategy, and enqueues normal `ICommand`s through the existing Commander and `GameSimulation` paths. The model never receives simulation objects or chooses concrete IDs, coordinates, commands, owners, provenance, approvals or reservations. Voice, general autonomous tool calling, hidden-information scouting, multiplayer certification and broad save/load are outside 4E.

The design reuses `CommanderChatUI`, detached contexts, tactical intent/goal admission, `CommanderGoalManager`, `CommanderPlanner`, and the strategic bridge/pipeline/policy. The existing exact offline lifecycle/explanation controls retain precedence. The old `CommanderIntentDtoCodec` strategic `FromPlayerInterpretation` branch is never fed Phase 4E model output: that would accidentally create PlayerDirect provenance from untrusted text.

## Chosen shape and rejected alternatives

Add a separate, data-only Phase 4E semantic request contract and strict parser upstream of the existing tactical and strategic authorities. This is a language boundary, not a second gameplay-execution system. Extending the old tactical DTO with selectors/graphs would conflate its PlayerDirect strategic conversion with model data. A two-provider-pass classifier/interpreter would make compound references fragile and spend additional quota. Free-form model tool calling would breach the core authority invariant.

An `ICommanderSemanticProvider` consumes bounded player text, a lean detached semantic context, and detached bounded recent semantic facts. The provider context contains supported capability names, the current age label, bounded owned type counts and recent semantic requests—not live entity IDs, world coordinates, enemy data or an omniscient map. Its output is one JSON object with a bounded outcome (`Request`, `Clarify`, `Unsupported`) and at most four typed request nodes. Supported node types are `EnsureUnitCount`, `BuildStructure`, `SetResourceAllocation`, `ReachAge`, and existing named strategic objectives. Nodes contain only whitelisted enum strings, bounded counts, semantic selectors/relations and intra-request node references. The provider cannot express a world coordinate, entity/worker ID, owner, source/provenance, raw goal/plan object, free-form script, loop, command or reservation. Model-produced explanatory prose is advisory; player-facing factual status comes from game-side state.

The new parser caps raw response at 8192 characters, JSON depth at 8, nodes at 4, edges at 4, and semantic references at 4; counts retain existing population/structure limits and tile distance is restricted to 1–20. It rejects trailing or duplicate JSON, comments/unexpected properties, numeric enum tricks, malformed values, NaN/infinity, cycles, dangling or wrong-type references, unsupported capability and ambiguous/inconsistent semantics. It does not coerce invalid output into a different command. Player text is capped at 1024 characters, serialized provider context at 8192 characters, recent semantic facts at 12, and one pending clarification; cancellation and timeout remain guarded. Automated tests use fake providers/transports; a bounded final Luna/OpenRouter corpus supplies live language evidence without retry-cherry-picking or exposing secrets.

## Host, authority and strategic routing

`CommanderChatUI.SubmitMessageAsync` first handles exact offline controls, then sends remaining bounded text to the semantic interpreter. The host captures trusted player/runtime generation and detached context before awaiting a provider. On return it checks generation, active simulation, owner and cancellation again. Game-side validation produces a typed semantic request with no provider object retained by any goal.

Tactical and desired-state nodes enter the existing dispatcher/resolver/goal-manager authority route after full graph admission checks. Graph admission is atomic: validate all nodes/edges/constraints and preflight manager capacity before assigning IDs or registering any goal; a batch-registration API commits the complete graph in one main-thread operation or admits none. An explicit player utterance is the source of authority for a `ReachAge` goal; the model cannot set that source. Existing strategic objectives remain pending recommendations in `StrategicAIApprovalBridge`: a new guarded staging API accepts an already validated semantic objective, rejects busy/stale/wrong-owner state, and creates bridge-owned intent ID/context/generation. It retains ordinary Approve/Confirm, adaptation, decision and commitment policy checks. This avoids a second provider call and does not use the generic PlayerDirect DTO path. Mixed tactical/strategic graphs are never partially executed in 4E: the host asks the player to split them into separate requests, and no node is admitted until the player does so.

## Deterministic selectors and spatial placement

The model may specify `MyTownCenter`, `NearestOwnedBarracks`, `SecondOwnedTownCenter`, a bounded recent result, or known resource relation, but not concrete IDs. A game-side resolver selects from owned or otherwise legitimately known/explored/visible state; hidden enemy or unexplored resources are excluded. Candidate ordering is explicit and stable (semantic distance, then stable entity/node ID). Ties that change player intent materially trigger clarification rather than arbitrary choice. Bounded recent-result references are revalidated against owner, runtime generation, existence and type before use.

Map-left is map-west, negative X; right is positive X, not camera-relative. `MyTownCenter` defaults to the oldest surviving owned TC by ascending `BuildingData.Id` (assigned monotonically by `BuildingRegistry`), so a player with several TCs need not clarify ordinary “my TC”; “my second TC” uses that same ordering. For “Barracks left of my Town Center five tiles apart,” the requested location has five **clear intervening tiles between the two building footprints/edges**, not center-to-center distance. With anchor minimum X `A`, requested clear gap `G=5`, and new building width `W`, exact west origin X is `A-G-W`; the clear tiles are `A-G` through `A-1`. Origin Z aligns footprint centerlines using `anchorMinZ + floor((anchorHeight-newHeight)/2)`, with the lower Z breaking a half-tile tie. The resolver tests the complete footprint plus required border for bounds, terrain, occupancy, current visibility/known-area policy, construction rules and a legitimate builder path. It tries the exact origin first, then candidates with `|dx|<=2`, `|dz|<=2`, and clear-gap error at most one tile, never reversing west/east; ranking is `(gap error, |dx|+|dz|, x, z)`. `Near` without a direction targets one clear footprint tile on any cardinal side; the bounded fallback admits gaps 0–3 and centerline offsets at most two tiles, ranked by `(absolute gap error from 1, displacement, x, z)`, with ordinary build validation still authoritative. If no candidate passes, report a typed placement blocker, never relocate to an unrelated part of the base. Behavioral tests pin both relations and player-facing wording explains fallback placement.

## Compound requests and result binding

A bounded acyclic graph represents player-specified semantic dependencies, not low-level LLM scheduling. In the mandatory Barracks request, node A is `BuildStructure(Barracks, semantic placement, create-new result)` and node B is `EnsureUnitCount(Spearman>=10, producer=ResultOf(A))`. Game-side admission validates the edges and producer compatibility. A new-instance build result cannot be satisfied by an already existing Barracks; the created building ID is observed/bound by game code after ordinary placement, then revalidated for ownership/type/survival before production. If it is destroyed or changed, the goal blocks/replans within supported semantics rather than silently using an unrelated producer. No provider-supplied live ID is accepted.

“Then” gates only the dependent producer use. Resource gathering and population preparation can begin while the Barracks is being built. Independent graph nodes may run concurrently; graph depth, active nodes, child goals and retention remain bounded. Shared prerequisites first inspect completed/in-progress buildings, active/queued goals and reservations to avoid duplicate Houses/Barracks or double-counted stockpile.

## Desired-state and concurrency planning

`EnsureUnitCount` remains a living-owned count target, accounting for queued units without treating queueing as completion. The existing one-action-per-15-tick manager cadence is preserved, but a deterministic dependency projection considers infrastructure, food/wood/gold, population and worker availability together before choosing the next action. It can interleave ordinary gather/build/train commands across independent branches, then reevaluate on that cadence or relevant existing events. Concurrency means persistent actions overlap, not multiple commands in the same tick or free resources. Reservations are accounting only; atomic commands still check actual available stock. Human/recently ordered and foreign/reserved/unreachable workers remain excluded; manual override releases Commander ownership, after which another legal worker may be selected or the goal waits.

`ReachAge(target)` observes the real integer player age and uses `LandmarkDefinitions` for that civilization's next legal age, landmark choices, costs, footprint and required sequence. It checks `HasChoices(civ, nextAge)` before `GetChoices`, because `GetChoices` otherwise falls back to English age-two choices for unsupported pairs. Where the civilization offers several legal landmarks for the same age, game code chooses the lowest stable `LandmarkId` as the documented default and announces that choice; the model cannot pick a landmark. It uses a normal `PlaceBuildingCommand` with a game-chosen owned worker/location and landmark ID, observes in-progress construction, recovers from legal temporary blocks, and completes only after `GameSimulation.GetPlayerAge(owner) >= target`. It succeeds immediately if already at/above target; invalid/unsupported civ-age paths produce typed failure. It never directly changes age/resources/buildings. Goal admission, pause/resume/cancel/reset, budget, health/advisory projections, worker/reservation cleanup and strategic parent observation follow existing Phase 4D lifecycle patterns.

The reported ten-Spearman wood stall must first be reproduced with state evidence. `PlanGather` currently conflates no visible node, no eligible worker and no reachable top-K candidate under one “No eligible owned villager” message; correcting that message alone is not a convergence fix. Any proven worker/reachability/resource-path defect gets the smallest cause-level fix, a failing behavioral test first, and a human-override regression.

## Follow-ups, clarification and UI

Store only a bounded window of detached semantic facts: last accepted unit target/count, validated result selector, desired age and request identity. No live Unity object, provider task, raw unbounded transcript or cross-match cloud memory enters it. “Make five more” uses the last unique compatible unit target and sets the next desired total to `max(previous accepted target, current living count)+5`; an incomplete target can never be lowered by a follow-up. “Same thing but with archers” reuses only the uniquely recoverable prior count/shape. If multiple referents fit, ask which one. Clarification state binds request ID, trusted owner, runtime generation, expected field/schema and a 3600-simulation-tick expiry; reset/new match invalidates it and late replies fail closed.

The normal Commander UI remains typed and playable beside manual controls. It acknowledges accepted desired states, shows fact-grounded progress and typed blockers, supports existing cancellation/strategy controls, and offers concise clarification/unsupported messages. It does not require JSON, enum spelling, goal IDs, inspector edits or console commands. The provider may phrase a vetted explanation, but cannot invent state. UI status frequency is bounded and avoids per-frame expensive world scans.

## Verification and release gates

Implement in 4E.0–4E.8 order, each code subphase closing focused RED/GREEN where applicable, compiler/import, scoped review, relevant regression and authority audit before the next. Preserve one production writer per overlapping area and one Unity runner. A full-source review checks provider-side forbidden references, fog/owner/provenance/stale guards, boundedness/performance and deterministic tie-breaks. Automated layers include value/unit, integration, EditMode and real PlayMode. Required runtime scenarios A–J are mapped in `Docs/CommanderPhase4E/requirements-matrix.md`; each must report exact assertions, test IDs and results. Full final suites must exceed the accepted 703 EditMode / 159 PlayMode baseline unless every reduction is explained, with zero failed/unexpected skipped/inconclusive/compiler errors.

The checked-in natural-language corpus records first-run semantic outcomes from a bounded live OpenRouter/Luna pass, including paraphrases, compound spatial, age, follow-up, ambiguity, unsupported and hostile text. Automated deterministic tests do not consume API quota. The final Windows x64 player build uses the single enabled `SampleScene`, must launch into a playable match, show the Commander UI, accept natural text, execute at least one simple request, leave manual controls working, avoid fatal player-log errors and quit cleanly. At least one substantial 4E scenario must run in the closest available standalone environment. Provider configuration stays external via the existing environment-variable pattern; no key is embedded or documented.

After source freeze, generate final source/test/meta hashes and a boundary audit relative to the clean `a2c4104` baseline; classify adjacent/provider/build artifacts separately. Retain raw final Unity results, live corpus, A–J reports, performance observations, build path/hash/logs and known limitations in `Docs/CommanderPhase4E/`. The final report follows objective sections A–Q and ends exactly `READY FOR PHASE 4F` only when every required gate is proved; otherwise `REQUIRES FIX PHASE`.
