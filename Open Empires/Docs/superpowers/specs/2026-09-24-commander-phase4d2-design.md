## Intent and acceptance

The player should see why an approved plan is running, paused, waiting, blocked, or terminal without giving an AI provider or a health observer gameplay authority. This phase adds observation and explanation only; recovery/adaptation proposals and advisories remain for 4D.3/4D.4.

## Alternatives and decision

1. Extend existing `StrategicPlanState`/`StrategicContext`: few new types, but current context includes only nonterminal plans, string status fields, and no trustworthy per-plan child-goal association or revision. It cannot alone satisfy terminal/stale/mutation-isolation tests.
2. Add a planner-boundary, on-demand detached health projector: **selected**. It can use the authoritative plan/child-goal association, copied owner economy, and current simulation tick while returning only immutable values. No event-maintained shadow state is needed.
3. Maintain a subscribed health cache: potentially useful to 4D.4 transition advisories, but it adds a second lifecycle and reset problem now. Defer it unless a later gated phase proves a need.

## Source of truth and API boundary

Add one health value module (for example `StrategicPlanHealthSnapshot.cs`) and one focused `StrategicPlanner.Health.cs` partial. The planner exposes an on-demand capture by trusted owner and exact plan ID; it obtains the fresh owned-state projection itself through its existing goal-manager/simulation boundary, rather than accepting caller-supplied context data. Its inputs are the live planner's `StrategicPlan`, `StrategicMilestone`, retained plan-linked child goals, active plan reservations, and copied owned state. Reuse `CommanderContextBuilder` where its counting predicates match the intended fact; population detection below requires a separate exact read-only mirror of `CommanderPlanner.PlanUnits`. It does not call `StrategicPlanner.Tick`, `CommanderGoalManager.Tick`, `CommanderPlanner.Plan`, provider APIs, CommandBuffer, or mutating simulation methods. It does not subscribe to gameplay events.

The capture returns no snapshot for an unknown or foreign-owned plan. Terminal plans may be captured explicitly by ID while still retained by the planner; bare current-plan UI selection remains limited to authoritative current nonterminal plans. A captured snapshot includes owner ID, plan ID, creation tick, revision, observed simulation tick, typed plan status, current milestone ID/name/status, bounded completed/total milestone counts, current milestone child-goal required/completed counts, retained live child-status counts, missing-history count, a typed primary category and bounded typed secondary facts, copied resource summaries, population/cap, and only justified owned-production counts. Historical completed children come from `StrategicMilestone.CompletedChildGoals`; an evicted archived goal's finer terminal status is Unknown, not inferred from its absent object. `childGoalLinks` does not retain terminal links, so enumerate the milestone's required IDs and use retained `goalManager.GetGoal` only for current details. Test archived-goal eviction. Use read-only copied collections, scalar values, and bounded strings; never expose mutable `StrategicPlan`, `StrategicMilestone`, `CommanderGoal`, `GameSimulation`, `BuildingData`, `UnitData`, Unity objects, commands, callbacks, or live collections. Unknown enum values fail closed to an Unknown category and no speculative explanation. Explicit serialization uses stable field order, invariant scalar formatting, and only the documented copied fields.

Resource fields must distinguish whole-plan canonical budget, current milestone requirement, current owned amount, current milestone deficit, active reservations owned by this plan, and total active reservations across all plans. A whole-plan budget is never described as remaining need. Deficit and available amount follow existing reservation rules and use checked, nonnegative arithmetic. If canonical current-milestone requirements are unresolved, report Unknown rather than zero need.

The host may render a short health line and answer exact-form health questions offline using a **fresh recapture immediately before each answer or render**. It must validate the current trusted `Conversation.PlayerId`, strategic pipeline instance/runtime generation, and snapshot owner/plan ID/creation tick/revision before describing a snapshot as current. Plan revision alone does not track resource, population, or queue changes, possibly even inside one simulation tick; cached snapshots cannot be declared current from that token alone. A stale or old-match snapshot says evidence is unavailable, never describes its successor. No provider call is needed. Do not add a new UI redesign or a control action in this phase. Reset, reinitialization, pipeline replacement, and destruction clear any retained host health view; preferably retain no core projection state at all.

## Structured classification and stall semantics

Use typed facts only, scoped to the current milestone's required children. Deterministic primary ranking: terminal `Completed`/`Cancelled`/`Failed` > explicit `Paused` > retained child `Blocked` > structured `WaitingForPopulation` > milestone/child `WaitingForResources` > `WaitingForPrerequisite` > `WaitingForProduction` > `WaitingForConstruction` > `Healthy`/`Unknown`; break ties by child-goal ID. Preserve other simultaneously proven facts in a bounded, ID-ordered secondary list, so a resource-wait milestone cannot conceal a blocked child and a House-wood wait cannot erase a population-cap fact. A milestone's or child's `WaitingForResources` is expected waiting, not failure. Do not assert an age, worker, or unit-specific producer cause from a generic status or parse `StatusReason`/`OutcomeMessage`. A `Blocked` child is `TemporarilyBlocked`; its existing `BlockedSinceTick` is a deterministic no-progress duration, not proof of impossibility. `Healthy` needs evidence of active/executing or completed progress with no proven wait/blocker; absence of a blocker alone yields `Unknown`. `Failed` is authoritative only after the existing goal/planner failure transition. No new wall-clock, frame, random, or generic timeout controls a plan.

Population waiting may be asserted only when an unfinished current-milestone `EnsureUnitCountGoal` and fresh owned population/queued counts satisfy the exact capacity condition in `CommanderPlanner.PlanUnits`. On the simulation-owning thread, mirror its predicates: resolve the civilization unit type; count owned living matching units in the unit registry (not the garrison-inclusive `CommanderContext.Units` aggregate); count matching queued units and all queued units across owned, non-destroyed buildings; compute `remainingOrders = TargetTotal - owned - matchingQueued`; classify capacity only if `population + allQueued > cap` or `remainingOrders > 0 && population + allQueued >= cap`. Copy the supporting population/cap/max, owned/queued/remaining values. At max population, reflect the tactical planner's current `Blocked` condition without claiming the whole strategy is permanently impossible; unit loss may free capacity. Do not invent a recoverable House beyond max cap. This is an observation and must not recalculate or apply a plan. If a House is also waiting for wood, preserve both typed facts. Worker, reservation, and production-capacity labels require similarly direct typed proof; otherwise use the broader honest category and optional copied numbers. Fogged enemy state must not influence classification or explanation.

Use existing deterministic tick anchors for blocked duration. While paused, compute `max(0, min(observedTick, PausedAtTick) - BlockedSinceTick)` with widened/overflow-safe arithmetic; after resume the existing control path shifts the goal's blocked anchor. A paused plan therefore does not accrue apparent blocker time. This phase does not add a new inactivity threshold; the tactical blocked retry/timeout and planner resource retry already govern actual transitions. Repeated capture at the same authoritative state must produce the same snapshot and must not advance either plan or simulation.

## Integration, security, and compatibility

Existing Phase 4D.1 lifecycle control identity/revision and host generation guards remain unchanged. Existing `StrategicApprovalLayer` → `StrategicDecisionPolicy` → `StrategicPlanner` → `CommanderGoalManager` is the only execution path. Health may not create an intent, recommendation, adaptation proposal, goal, reservation, command, control request, or provider call. It cannot retain a live source object or fabricate hidden enemy reasoning. No new objective, network message, package, credential handling, memory persistence, or API-key change is in scope. Preserve public and reflection-sensitive signatures; add overloads rather than breaking them if integration demands it. Do not redesign the Phase 4C House reservation limitation without an actual RED correctness failure and authority review.
