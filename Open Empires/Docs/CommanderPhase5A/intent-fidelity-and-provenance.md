## Authority boundary

Phase 5A distinguishes interpretation from authorization. Provider output is untrusted semantic data; provider role labels, text, graph roots, dependencies, and provenance claims cannot approve effects. A `CommanderRequestTicket` is minted locally before interpretation and binds one candidate to its manager, simulation, generation, original bounded input, and current-request predicate. Minting or tracing the ticket grants no execution authority. The ticket is claimed once, and candidate approval rechecks owner, generation, freshness, and exact candidate state.

Existing game-owned direct request and approved-candidate paths remain the basis for human authority. Configured computer ownership remains a separate existing path. Local player number, host status, UI presence, provider fields, emergency priority, or recommendation history are not proof of human consent. Request tickets bind the chat interpretation path; established trusted legacy game APIs do not all issue chat `CommanderRequestTicket`s, so do not claim ticket coverage for every API. Background strategic evaluation may publish advisories; it must not commit human strategies. Emergency changes urgency only within already authorized scope.

Automatic KnownIntent admission is limited to pre-existing resolver/response paths with explicit local evidence (`KnownIntentAutomatic` or clarified equivalent). Effectful synthesized plans, including DynamicPlan and independently ungrounded compound graphs, require one normalized plan preview and one single-use confirmation. A provider-authored root or span is not independent grounding. UI preview is side-effect-free: no work, command, or reservation is created until approval. Approval is bound to the exact immutable candidate and relevant runtime/owner/revision; changed candidates need new approval.

## Request effects and constraints

The locally normalized root effects and negative constraints are authoritative for the request. The shared strict semantic/DTO schema supports at most four distinct constraint types: `NoConstruction`, `PreferredWorkers` (`IdleOnly`), `MaximumQueue`, `ProtectedResource`, and `ResourceSource`. The current schema permits only one `ResourceSource` constraint per candidate; multiple independent source restrictions are not supported. Constraints are checked before derived prerequisites and at dispatch, including implicit preparation created by existing planners. Production does not authorize attack, scouting, unrelated reassignment, age-up, or additional construction. `NoConstruction` prohibits both new and resumed construction. Existing eligible capacity may satisfy production; an unmet legitimate prerequisite may be planned only when the root permits it. An unrelated question does not cancel existing accepted work. Cancellation/supersession/reset clears pending candidate state and releases reservations; already issued or completed gameplay is not rolled back.
