# Phase 5A exact training receipts — design draft (not implemented)

## Boundary and present gap

An explicit `produce-units quantity 10` result must contain ten *actual, newly spawned* unit IDs from training orders issued by that exact goal at its exact bound set of two new Barracks. A queue entry, a paid cost, a matching unit type, or a unit absent from the submission baseline is not a result. Other goals, human orders, pre-existing queues, and unrelated producers never fill the result. The receiving action remains bound to the same `GameSimulation` and `CommanderGoalManager`; a human command on an already attributable unit sets a permanent takeover bit before or after result capture. Death, cancellation, producer loss, or pop-cap delay cannot invent a replacement result.

Current code cannot prove that contract: `TrainUnitCommand` has only `PlayerId`, `BuildingId`, `UnitType`; `ProcessTrainUnitCommand` silently enqueues a resolved type; `BuildingData.TrainingQueue` is a public `List<int>`; `TrainingCompletion` knows only building/type/player; `OnUnitTrained` knows only unit/type/player; and `CommanderPlanner.PlanEnsureUnits` takes any new living matching unit after excluding baseline IDs. The existing one-producer PlayMode test does not exercise competing orders.

## Proposed observational flow

1. **Issued order identity.** At the existing `CommanderGoalManager.Tick` enqueue site, register the *boxed `ICommand` object* for each `EnsureUnitCountGoal` training order with the game-owned simulation before `CommandBuffer.EnqueueCommand`. Use an `IEqualityComparer<ICommand>` based on `ReferenceEquals` and `RuntimeHelpers.GetHashCode`, not struct value equality. The simulation's runtime-only registry records `(goal object, manager object, simulation object, requested/resolved unit type, authorized exact producer ID/set)` and consumes the entry at dispatch, whether the command is accepted or rejected. A replay-correlation failure, cancellation, reset, or disposal discards unresolved entries. This is an internal manager-to-simulation API, never provider-supplied data. `CommandBuffer.CommandEnqueued` retains its human/Commander source event; that source is not an origin token on replayed network commands. The original box survives single-player `FlushCommands` and `ProcessCommand`.
2. **Replay correlation only at the existing multiplayer boundary.** In `GameBootstrapper.ProcessMultiplayerTick`, save the ordered original local `ICommand` references alongside each *stamped* batch for `commandTick` before `NetworkManager.SendCommands`; `SetCommandPlayerId` reboxes structs, so never use stamped-box reference as the goal key. Before `Simulation.Tick(tickCommandsBuffer)`, take the local owner's ordered slice from `ConsumeCommandsForTick(currentTick)` (which sorts players but appends each player's received list in order). Compare the *complete* local stamped batch to that slice: same count; same command type, owner, and exact canonical existing `CommandSerializer.ToJson` command type/payload at every ordinal. Only on complete equivalence form a one-tick map `replayed box -> original box` by ordinal. Any missing, extra, reordered, changed, unsupported, or non-round-tripping command invalidates the entire batch correlation; gameplay still executes normally. Prune consumed/abandoned future-tick batches. No new wire field, serializer format, checksum input, or simulation command is introduced.
3. **Accepted queue-entry identity.** Change `GameSimulation.ProcessCommand`'s train arm to pass the original `ICommand` object (or the verified one-tick local origin) into `ProcessTrainUnitCommand(TrainUnitCommand cmd, ICommand commandOrigin)`. Consume its registered candidate at entry; only after all existing ownership, build, age, compatibility, and resource checks and the resource deduction succeed may the simulation attach an opaque runtime-only `TrainingReceipt` to the *specific newly appended queue slot*. Require the candidate's exact owner, current manager/simulation identity, requested command fields, resolved unit type, and authorized producer ID to agree before attachment. An uncorrelated/human/AI/autoproduced order gets an unattributed slot. The receipt includes immutable goal/manager/simulation identity and bound producer ID, plus a local monotonically assigned order ordinal for diagnostics; it does not alter game decisions. A local acceptance callback may tell the manager to mark that pending order accepted, but acceptance alone never counts as production.
4. **Queue integrity through cancellation and completion.** Keep the existing integer queue behavior and checksum values, but make its public mutation surface a tracked `IList<int>`-compatible collection (including the existing `AddRange` use) whose entries have aligned opaque receipt slots. `BuildingData.EnqueueTraining` appends a normal/receipt entry; `DequeueTraining` returns the front `(unitType, receipt)` to `BuildingTrainingSystem`; a dedicated `RemoveTrainingAt(index)` is used by `ProcessCancelTrainCommand` so a canceled receipt is discarded at the exact index. The wrapper's legacy/direct `Add`, `AddRange`, `Insert`, `Remove`, `RemoveAt`, `Clear`, and indexer set are permitted for compatibility but invalidate *all* attribution in that building's current queue, even if count and unit values end up identical. No mutable `List<int>` reference, replaceable field, or cast exposing backing storage may escape. If replacement of the public `List<int>` type is disallowed, exact fail-closed behavior under same-value direct mutations is impossible; a count/type snapshot sidecar is insufficient.
5. **Actual spawn observation.** Add the opaque receipt to `TrainingCompletion`, carry it through `RunSystems` to `SpawnTrainedUnit`, and publish a new local-only post-`CreateTrainedUnit` event `(receipt, unitData.Id, building.Id, unitType, playerId)` after registry insertion. Preserve `OnUnitTrained` and all rally behavior exactly. The manager accepts only a receipt owned by its current runtime and nonterminal source goal, for the authorized producer and resolved unit type, and a still-owned living spawned unit. Deduplicate unit IDs and append in accepted order. A discarded/canceled/unknown slot produces no result. Do not infer a receipt from `OnUnitTrained` or a matching `(building,type)` completion.
6. **Goal result and follow-up.** For a result-producing goal, `CommanderPlanner.PlanEnsureUnits` must compute remaining orders from attributable spawned IDs plus attributable accepted *still queued* orders, not global `owned + queued`, while retaining canonical age/resources/pop/queue limits. Its completion/capture gate uses a trusted `RequiredNewProductionCount`: ten for an explicit dynamic `produce-units quantity 10`, or the existing `TargetTotal - BaselineUnitIds.Count` for a legacy result-linked total-count request. Ordinary goals without a result consumer keep their current total-count behavior. A two-Barracks producer set uses only the two exact `BuildStructureGoal` result IDs, validates both are alive/owned/compatible, deterministically distributes orders across both, and requires a recorded completion from **each** when the instruction means both produce. If a required producer is lost, block/fail without switching to an old Barracks. Capture a fixed ordered list of actual unit IDs once. Update pre-capture takeover detection to consult the manager's actually spawned receipt IDs, not `!BaselineUnitIds.Contains(id)`; keep `ResultHumanOverride` sticky and recheck ownership/liveness at dispatch. No selector fallback or cross-runtime result rebinding.

## Narrow signature/file changes to implement later

- `Assets/Scripts/AI/Commander/CommanderGoalManager.cs` and `CommanderGoal.cs`: register/remove issued train-command identity; hold accepted order and spawned-unit receipts; source-goal runtime checks, exact result freeze, and sticky takeover. Existing `CommanderResultBinding` checks remain.
- `Assets/Scripts/AI/Commander/CommanderPlanner.cs`: exact result-goal remaining/completion counts and producer-set choice; ordinary non-result count behavior remains unchanged.
- `Assets/Scripts/Core/GameBootstrapper.cs`: per-future-tick original/stamped local batch, full ordered equivalence, one-tick replay-to-original map. `Assets/Scripts/Network/NetworkManager.cs` and `CommandSerializer.cs` should remain wire-identical; inspect relay FIFO contract before claiming multiplayer precision.
- `Assets/Scripts/Core/GameSimulation.cs`: internal `RegisterTrainingOrigin(originalCommand, goal, manager, exactProducer)` plus consume/discard hooks; `ProcessTrainUnitCommand(cmd, originalCommand)` acceptance site; `ProcessCancelTrainCommand` indexed removal; `SpawnTrainedUnit(..., receipt)` actual-spawn event; optional `Tick(commands, localOriginMap)` overload rather than ambient persistent correlation. Do not change command processing order, costs, spawn, or checksum.
- `Assets/Scripts/Buildings/BuildingData.cs`: tracked queue facade and internal per-slot receipts; `EnqueueTraining`/`DequeueTraining`/indexed cancel signatures. `BuildingTrainingSystem.cs`: `TrainingCompletion` carries opaque receipt. Keep serialized/deterministic queue integers as before and explicitly verify queue facade call-site compatibility.

## Proof fixtures (RED first, then focused GREEN)

1. Same simulation/manager: pre-existing Spearman queued at new Barracks, then goal-issued Spearman; pre-existing completion yields no result, goal completion yields its exact ID. Same producer/type with interleaved human and different-goal orders, including cancel of front/middle entry and pop-cap freeze, credits only each goal's own actually spawned order.
2. Two newly placed Barracks plus one old compatible Barracks: quantity ten yields ten distinct live result IDs, each with an accepted order from one of the two exact new IDs and at least one from each; old producer, human, and other-goal completions cannot substitute. Destroy one bound producer and verify no fallback. Existing global count may be ten while attributable count is short: dependent action must wait/block, not execute.
3. Rejected train commands (insufficient resources, wrong owner, construction, age, incompatible producer) attach zero receipts; queued-but-unspawned, canceled, or destroyed-unit orders never fill a result. Direct legacy queue `Add`, `RemoveAt`, index set, and same-value remove/re-add invalidate outstanding attribution without changing gameplay output.
4. Single-player original-box identity: two value-equal boxed train commands from distinct goals map separately. Multiplayer: stamped/reboxed and deserialized local ordered batch maps each ordinal back to its original; identical same-field commands from different origins remain distinct *only if* transport FIFO is an established contract. A missing/extra/reordered/changed command fails the entire batch correlation, while simulation still executes the same received commands. Remote player orders never map to local Commander goals.
5. Human takes a receipt-produced unit before result capture, then later after capture; both permanently block the dependent action, including manager replan. Foreign manager/simulation receipt, reset/dispose, canceled goal, duplicate spawn observation, and dead unit cannot bind or substitute.

## Multiplayer limit requiring explicit proof

`NetworkManager.SendCommands` sends separate commands in list order and `HandleGameCommand` appends decoded messages in arrival order; `ConsumeCommandsForTick` sorts by player ID and preserves that arrival list. The inspected client code does **not** itself prove the relay guarantees per-player FIFO delivery. Without such a guarantee or an existing ordered batch contract, two identical same-field train commands from different goals/human sources can be swapped invisibly: the complete value comparison still passes, yet origin attribution is wrong. Until that contract is audited and tested, fail closed for ambiguous duplicate equivalence classes with differing origins (or disable multiplayer result attribution), and report multiplayer exactness as unproven. This cannot be solved by a building/type heuristic or local-only ordinal alone; the requested no-wire-change constraint precludes a general repair if relay order is not guaranteed.
