`Map/MapData.cs:76-105` maps integer tile `(x,z)` to world tile center `(x+0.5,z+0.5)` and back. Existing tactical placement uses a TC footprint center and square-ring search (`CommanderPlanner.cs:664-695`), while `IsVisibleBuildableArea` and known-path checks live at `CommanderPlanner.cs:697-757`. The subsequent user-approved Phase 4E convention is map-west/negative X for “left,” with a requested tile distance measured as clear tiles between building footprints; it is not implemented yet.

## Phase 4E design constraints and unresolved diagnostics

- The natural-language entry point must replace exact phrase gating without losing offline lifecycle precedence or changing trusted player identity/provenance.
- A semantic provider DTO must be data-only. Game-side code must validate all nodes, selectors, counts, age targets and graph edges before any goal admission. Strategic model output must not enter the generic DTO's `FromPlayerInterpretation` branch.
- A compound `from that Barracks` request requires a new-instance result reference; the current `BuildStructureGoal` is total-count based and can complete from an existing Barracks. Its result must be bound to a game-resolved building, never a provider-chosen ID.
- Reaching Castle Age must use the actual civilization's legal landmark sequence/costs, normal `PlaceBuildingCommand`, construction completion observation, and existing lifecycle/cleanup rules.
- The documented ten-Spearman wood stall is not diagnosed by source inspection alone. Plausible causes include worker protection/reservations, top-candidate reachability capping, missing visible nodes, and drop-off accessibility. Reproduce and trace before fixing; preserve human worker authority.
- One narrower diagnostic defect is source-confirmed: `SelectEconomyWorker` returns a null worker when no visible node exists, when no eligible worker exists, **or** when all top-K candidate paths fail; `PlanGather` checks the null worker before its null-node branch (`CommanderPlanner.cs:302-320,461-558`). Thus the displayed “No eligible owned villager” text does not distinguish those causes. It cannot establish which cause produced the user's screenshot without a runtime reproduction.
- Final requirements need separate proof: focused tests, full EditMode/PlayMode regressions, live provider corpus, real A–J scenarios, standalone Windows build and launch smoke test. No such Phase 4E proof exists yet.
- Live Unity MCP read-only build inspection reports one enabled build scene, `Assets/Scenes/SampleScene.unity`, and the current `StandaloneWindows64` Player target. A build result, launch, interaction and log smoke test remain separate future evidence.
- Reusable test seams are `Assets/Tests/EditMode/CommanderIntentTests.cs` (parser/validator/dispatcher integration), `CommanderPhase4A1HardeningTests.cs` and `CommanderPhase4B1Tests.cs` (provider hardening), `CommanderPhase3ATests.cs` and `CommanderPhase1Tests.cs` (construction/placement), `CommanderPhase3CPreparationTests.cs` plus its PlayMode counterpart (independent goals and worker ownership), `CommanderPhase3Fix11Tests.cs` (bounded path candidates), and `CommanderPhase4C1PlayModeTests.cs` / `CommanderPhase4D1PlayModeTests.cs` (held provider/reset). The existing Phase 3C PlayMode test proves Barracks and wood can overlap as **separate goals**; it does not prove a single 10-Spearman desired state derives and overlaps all its own prerequisites. No existing `ReachAge` or standalone interactive-build smoke fixture was found.
